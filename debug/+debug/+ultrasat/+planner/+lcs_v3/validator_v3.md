# LcsHelper v3 Validator

## General

`validate_LcsHelper_v3.m` is a hard rule validator for plans generated by `ultrasat.planner.LcsHelper_v3`. It builds one v3 plan, checks the internal MATLAB object state, writes the generated CSV outputs under `+debug/+ultrasat/+planner/+lcs_v3/output/validation/`, and exits with a failed validation summary if any required scheduling rule is violated.

The validator separates hard failures from warnings. Hard failures mean the plan does not satisfy required structural or timing rules and should not be accepted. Warnings are review items that may be scientifically important but are not currently required to reject the plan, such as extinction-ranking quality.

The validator is intended to catch false plans, including plans that have the right number of rows but invalid timing, duplicate fields, illegal slot occupancy, or a daily schedule that does not match the schedule table.

## Detailed Operation

### Build and outputs

The validator constructs `LcsHelper_v3` using the package-local grid file lookup and the same constructor arguments used by the v3 debug tooling. It runs the helper build flow, validates the resulting object, and then writes:

- `schedule.csv`
- `full_windows.csv`
- `daily_schedule.csv`
- set-specific debug tables when available

The output directory is `+debug/+ultrasat/+planner/+lcs_v3/output/validation/`.

### Set A hard checks

Set A must contain exactly 48 placed fields. Every Set A row must have a 45-day window. Original groups 1 through 6 may each contain at most 8 fields.

If Set A fields are shifted into later groups, those moved rows are explicitly checked. A moved row must use the start and end day of its assigned `Full_windows(ind)` entry, and moved `(group, ind)` slots must be unique. The validator also checks that the group accounting includes both original groups and moved groups, so shifted Set A fields are not hidden from the count checks.

### Set B hard checks

Set B must contain 16 unique fields and 48 rows total. Each selected field must appear once as `B_45` and twice as `B_90`. All Set B rows must be 45 days long and must align exactly with full-window boundaries.

For each Set B field, the three rows must cover a 135-day span over three distinct full-window indices. Group encoding is checked through the `100 + fw_ind` convention for `B_45` and `200 + fw_ind` for `B_90`.

### Set C hard checks

Set C must contain 16 unique fields. Each row must span 135 days and must start on a full-window boundary. For v3, the validator checks the v3 Set C group and start-index conventions, including the expected long-window grouping behavior.

### Set D hard checks

Set D is optional but may contain no more than 4 fields. If present, Set D fields must be unique, must use 45-day windows, and must use legal Set D group slots `301..304` without duplicate group slots.

### Slot budget hard checks

For each full-window index, the validator recomputes occupancy from `Schedule`:

- `nA`: Set A rows assigned to the index
- `nB45`: 45-day Set B rows assigned to the index
- `nB90`: 90-day cadence Set B rows assigned to the index
- `nC`: Set C rows covering the index
- `nD`: Set D rows assigned to the index
- `nCadence4 = nB90 + nC`
- `filledABC = nA + nB45 + nCadence4 / 4`
- `filled+D = filledABC + nD`

Hard checks require `nCadence4` to be divisible by 4, `filledABC <= Daily_LCS_slots`, and `filled+D <= Daily_LCS_slots`. This means Set D cannot silently overfill a full-window slot after the A/B/C budget passes.

### Window bounds hard checks

All placed schedule rows must start on or after `First_day` and end on or before `Last_day`. Empty plans fail.

### Duplicate hard checks

The same field ID may not appear in more than one logical set. The validator checks all cross-set pairs: A/B, A/C, A/D, B/C, B/D, and C/D.

### Daily schedule hard checks

The daily schedule matrix must be non-empty, must have one row per planning day, and must have exactly `Daily_LCS_slots` columns.

The validator then reconstructs the expected daily field multiset from `Schedule`. Normal rows appear on every day between `start` and `end`. `B_90` and `C` rows appear only on their 4-day cadence, using the same modulo rule as the helper:

`mod(curr_day - start + 1, 4) == mod(ind, 4)`

For each day, the validator compares the sorted/multiset field IDs from the reconstructed schedule to the field IDs in `Daily_schedule`. Extra fields, missing fields, duplicates, wrong cadence, or wrong day placement are hard failures.

### Warning checks

The validator emits warnings for ranking review items:

- Long-field extinction ranking across Set B, Set C, and long Set A candidates.
- Set D ranking consistency using the helper's `SetD_ranked_fields`.

These warnings do not fail validation. They are intended for review with Yossi because ranking may need scientific judgment rather than a strict accept/reject rule.
